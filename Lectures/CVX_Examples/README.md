# CVX Examples: convex optimization demos (MATLAB and Python)

Short demos used in lecture for **Wearable Robotics (WR26)**. Each one turns a
wearable-robotics task into a convex optimization problem: fitting a gait
curve, smoothing a noisy signal, and controlling a motor. The point is to
recognize the problem's structure (least squares, norm minimization,
quadratic program) and see how the choice of objective changes the answer.

Every demo except `Inverse_Dynamics_Kuo98/` (Python only, since it uses
OpenSim) exists twice, side by side in the same folder:

- **MATLAB** (`.m`): solved with `\`, [CVX](https://cvxr.com/cvx/), or a
  solver generated by [CVXGEN](https://cvxgen.com/).
- **Python** (`.py`): the same problem written in [cvxpy](https://www.cvxpy.org/),
  the Python counterpart of CVX. The two versions use the same variable names,
  comments and plots, so you can read them side by side, and they give the
  same numbers (checked to ~1e-14).

### MATLAB ↔ Python cheat sheet

| MATLAB | Python | used in |
|---|---|---|
| `load('file.mat')` | `scipy.io.loadmat("file.mat")` | Fourier |
| `p = R\y` (least squares) | `np.linalg.lstsq(R, y)`, or `scipy.sparse.linalg.lsqr` for sparse `R` | Fourier, Smoothing |
| `cvx_begin ... minimize norm(y - R*p, 2) ... cvx_end` | `cp.Problem(cp.Minimize(cp.norm(y - R @ p, 2))).solve()` | Fourier, Smoothing |
| `spdiags(...)` | `scipy.sparse.diags(...)` | Smoothing |
| `lqr(A, B, Q, R)` | `control.lqr(A, B, Q, R)` | LQR |
| `ode45(f, tspan, x0)` | `scipy.integrate.solve_ivp(f, tspan, x0)` | LQR |
| CVXGEN `csolve(params)` | cvxpy problem built with `cp.Parameter`s, re-solved with new values | MPC |
| `A*x`, `x.'`, `x(1)` | `A @ x`, `x.T`, `x[0]` (Python indexes from 0) | everywhere |

## 1. Truncated Fourier series: `Fourier_Transform_Truncated/`

**Problem.** Fit one gait cycle of the ankle angle with `j` harmonics of the
stride frequency `w = 2π/T`:

```
ankle(t) ≈ Σ_{k=1..j} a_k sin(k w t) + b_k cos(k w t)
```

The model is linear in the coefficients, so stacking one row per sample gives
`ankle ≈ R p`. The best fit is the least-squares problem `min_p ‖ankle − R p‖₂`.

- **`main_fourier`** solves it with `p = R\ankle` (MATLAB) or cvxpy, checked
  against `np.linalg.lstsq` (Python). Change `j` (8 by default): a few
  harmonics already capture the shape, and many harmonics start fitting the
  noise. The data has 1001 samples, so `j` can go up to 500.
- **`main_fourier_withOutlier`** adds +90° to one sample and fits with
  `j = 8` using CVX/cvxpy. One bad sample among 1001 moves the L2 fit only
  ~1.4°. **Try a burst instead**: corrupt samples 100–150
  (`ankle(100:150) = ankle(100:150)+90` in MATLAB, `ankle[99:150] += 90` in
  Python). Then the L2 fit shifts by up to ~66°, while the L1 fit
  (`norm(..., 1)`, or `NORM = 1` in Python) lets those samples keep large
  residuals and stays within ~5° of its clean-data fit. This is why robust
  fitting uses L1-type losses.

*Discussion point:* neither regressor has a constant column (`cos(0·w t) = 1`),
so the fit cannot represent the mean angle. For this dataset the mean is only
−0.5°, so the effect is small, but adding a column of ones is the correct model.

## 2. Minimum-jerk smoothing: `Signal_Smoothing/Smoothing`

**Problem.** Given noisy samples `y` of `sin(2πt)`, find `x` close to `y` with
small jerk:

```
min_x ‖x − y‖² + (α dt³)² ‖D3 x‖²   ⇔   min_x ‖ [I; α dt³ D3] x − [y; 0] ‖²
```

`D1`, `D2`, `D3` are sparse finite-difference matrices (5-point central
stencils; the two samples at each end are dropped). The stacked form is plain
least squares. Each version solves it two ways and prints both run times and
the largest difference between the solutions, which should be near zero:

- MATLAB: `\` vs. CVX (the CVX part is skipped with a warning if CVX is missing).
- Python: `scipy.sparse.linalg.lsqr` vs. cvxpy (`cp.sum_squares`). The Python
  noise uses a fixed random seed, so the result is the same on every run.

What to look at: in the second figure, the noise is barely visible in position
but dominates velocity and acceleration. That is why you filter before
differentiating motion-capture data. **Try** changing `α` (third argument of
`smoothCVX` / `smooth_cvx`). The default `1e-4` is too small to matter: the
result is almost the noisy signal. With `α = 1` the error to the true sine
drops from 0.029 to 0.017 (RMS), and with `α = 10` to 0.011. Too large flattens
the sine wave.

## 3. Motor control: `MPC/`

### `StateFeedback_LQR`: LQR (start here)

A brushed DC motor (Maxon 310005 datasheet values) with state
`x = [angle; speed; current]` and voltage input. The script

1. builds `A, B, C, D` from the mechanical and electrical equations,
2. checks controllability (`rank [B AB A²B] = 3`),
3. computes `u = −K (x − x_ref)` with `lqr` / `control.lqr`, which minimizes
   `∫ eᵀQe + uᵀRu dt`, `e = x − x_ref`, and
4. simulates the closed loop and plots the position and voltage.

Both versions give `K = [0.316, 0.0441, 0.0509]`. The Python version simulates
with `solve_ivp(method="LSODA")` instead of the `ode45` analog (`RK45`),
because the fast electrical pole (≈ −5700 1/s) makes the ODE stiff.

**Try** increasing `Q(1,1)` (faster tracking) or `R` (gentler voltage), and
check the peak voltage against what the motor driver can supply. LQR cannot
enforce a voltage limit; MPC can.

### `cvxgen/`: model predictive control

MPC solves a finite-horizon version of the same trade-off and **adds
constraints**. `description.cvxgen` defines (n = 5 states, m = 2 inputs,
T = 10 steps):

```
minimize    Σ_{t=0..T} (x_tᵀ Q x_t + u_tᵀ R u_t) + x_{T+1}ᵀ Q_final x_{T+1}
subject to  x_{t+1} = A x_t + B u_t          dynamics
            |u_t| ≤ u_max                     actuator limit
            ‖u_{t+1} − u_t‖_∞ ≤ S             slew-rate limit
```

This is a quadratic program. Both versions solve it once on a random `A`, `B`.
That shows the interface; a real controller re-solves every sample from the
measured state and applies only `u_0` (receding horizon).

**MATLAB** uses [CVXGEN](https://cvxgen.com/), which turns the description
into a custom C solver (`csolve`) that solves it in milliseconds, fast enough
for a real-time control loop.

- **`ExampleUse.m`** fills `params` and calls `[vars, status] = csolve(params)`;
  `vars.x{t}` and `vars.u{t}` are the predicted states and inputs.
- **`cvxsolve.m`** solves the same problem with CVX. Use it to check that
  `csolve` is correct, and to compare its run time.
- **Rebuilding.** `csolve.mexw64` runs only on 64-bit Windows. On another OS,
  run `make_csolve` in this folder (needs a C compiler). To change the problem
  (sizes, constraints), edit it on cvxgen.com, then run `cvxgen(<problem code>)`
  to download and compile the new solver. Do not edit the generated files by hand.
- **License.** CVXGEN-generated code may not be used commercially without
  permission from its author (see the file headers). Classroom use is fine.

**Python** (`example_use.py`, hand-written) writes the problem directly in
cvxpy. `A`, `B`, `x_0`, `u_max` and `S` are `cp.Parameter`s, so cvxpy compiles
the problem once. The script then solves a second time from a new `x_0`,
which is several times faster (about 3 ms vs. 20 ms) because only parameter
values change: the cvxpy counterpart of a generated solver. It uses the
Clarabel interior-point solver (OSQP often reports "inaccurate" on these
random, unstable systems), prints the predicted states, and plots the planned
inputs against `±u_max`. For embedded C code generated from a cvxpy problem,
see [CVXPYgen](https://github.com/cvxgrp/cvxpygen).

## 4. Least-squares inverse dynamics: `Inverse_Dynamics_Kuo98/`

In-class activity based on Kuo (1998); `Kuo1998.tex` is a condensed version
of the paper with its printed errors corrected, and the equation numbers in
the code refer to it. Python only (cvxpy + OpenSim).

**Problem.** Joint torques estimated by inverse dynamics feed the design
and control of wearable robots, but they are noisy. Newton-Euler (NE) works
up from the force plate one segment at a time, so the noise piles up at the
top: the hip torque is the noisiest, and a residual torque is left over on
the trunk. Kuo writes the ground reaction and the angular accelerations at
each time step `k` as one overdetermined linear system in the joint torques,
`A[k] τ[k] = b[k]` (eq. 6), and solves the weighted least-squares problem

```
minimize  Σ_k ‖ W^(-1/2) (A[k] τ[k] − b[k]) ‖²        eqs. (7)-(8)
```

`W` holds the measurement variances, so the precise force plate counts more
than the twice-differentiated markers. The benchmark is Kuo's four-segment
postural-sway model (foot, shank, thigh, trunk). Markers have 1 cm noise and
the force plate 0.1 N; the data is sampled at 60 Hz and filtered at 5 Hz.

**Files.**

- **`four_segment_opensim.py`**: run it once first. It builds the same
  model in OpenSim, checks that every equation of Appendix A matches
  OpenSim to round-off (~1e-13), and writes `_work/four_segment.osim` and
  `_work/sway.sto`. To watch the motion in the OpenSim GUI, use File → Open
  Model, then File → Load Motion. The motion is prescribed (joint-angle
  sinusoids from 0.5 to 2.2 Hz); OpenSim computes the true torques and
  ground reactions.
- **`least_squares_id.py`**: the activity. It simulates the measurements,
  runs NE and least squares, and plots both against the truth (Kuo's
  Fig. 3).

**What to look at.** Least squares cuts the overall torque error by about
half (Kuo reports 34%). The gain is all at the hip; NE is as good or better
at the ankle and knee. NE also leaves a residual torque of about 70 N·m on
the trunk, while least squares has none by construction.
